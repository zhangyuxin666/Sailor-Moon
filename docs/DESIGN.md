# 活动管家详细设计

本文描述当前实现的模块、数据流、状态和关键一致性机制，并保留团队共用的界面规范。整体拓扑与系统边界见 [ARCHITECTURE.md](ARCHITECTURE.md)，字段/路由见 [API.md](API.md)，表结构与迁移见 [DATABASE.md](DATABASE.md)，源码定位见 [SOURCE_GUIDE.md](SOURCE_GUIDE.md)。

## 1. 模块与服务边界

React 页面通过同源 Cookie 调用 Java Controller；Controller 取得服务端账号并进入业务服务。Spring Boot 3.5.16 / Java 21 负责权限、事务、持久化与所有工具副作用，WAR 同时托管前端。JdbcTemplate 统一访问 PostgreSQL，Flyway 升级结构。

FastAPI 只做草案/规划、嵌入、组织范围检索、回复和复盘文本，使用内部令牌；QQ Gateway 只做平台连接与 HTTP 消息传输，使用另一内部令牌。数据库业务事实和资源授权不能交给模型或网关决定。

业务按班级/作业、策划/知识、任务/消息、编排/基础设施分工；同一 Java 或 React 目录含多个主责，协作契约见 TEAM。

## 2. 草案确认与执行时序

1. 管理者选班级并提交自然语言，AgentDraftService 取得真实成员与组织范围，调用 AiClient 分析，保存可编辑草案和生成证据。
2. 保存/发布先验证并形成确认快照；日期、题目和负责人来自确认字段。简单事务走对应业务，复杂活动创建活动、运行和后台任务。
3. 缺必要信息的运行进入 waiting_input，补充输入持久化后由明确恢复动作重新入队。后台不能用空方案掩盖缺失数据。
4. JobScheduler 领取任务，ActivityOrchestrator 依流程开关和受限 tool_intents 执行规划、表单、任务、日历、提醒与交付，ExecutionJournal 保存真实步骤输入/结果。
5. 已确认活动复用快照，已提交步骤按稳定幂等键复用；模型不在重试时擅自重新决定已确认业务。

## 3. 三类状态与恢复

- 活动有自身生命周期，例如 queued/running/ready/failed/finished/cancelled，表示业务对象能否继续操作。
- agent_runs 使用 pending/running/waiting_input/succeeded/failed/cancelled，记录业务阶段和结果。
- background_jobs 使用 queued/running/succeeded/failed，记录领取、尝试和执行，不等同业务已交付。

队列用数据库抢占，独立心跳续约；JobLease 绑定一次领取凭证和版本，步骤前后验证，超时回收后拒绝旧执行者提交。失败按安全错误分类并有限重试。取消在步骤边界检查，阻止后续动作，保留已提交/在途外部事实。完整协议和诊断字段以 API 为准。

## 4. 事务、幂等与外部一致性

报名、任务、活动变更、参与设置和结束等操作先锁活动，再访问下属资源。管理请求使用 request_id 与 expected_version；同键同内容重放已有结果，键冲突/旧版本拒绝。数据库唯一约束与服务端校验共同保证容量、身份、任务计划键和依赖规则。

工作流按步骤提交，不持有整条流程的长事务。业务记录与步骤日志在同一步事务保存；步骤内外部调用可能等待，取消不能承诺立即撤回。变更通知由持久队列消费，业务修改和通知重试分开。

QQ 不能加入 PostgreSQL 事务。Spring 用独立事务保存发送意图和结果，网关以持久日志保留发送状态、请求摘要和外部编号。发送成功后业务步骤回滚/崩溃时，可读持久结果补齐步骤；未知结果停止自动重发并先核对。保证依赖数据库和网关日志都保留，不覆盖平台内部行为或整个持久卷丢失。

## 5. 权限与数据设计

身份来自数据库会话和 HttpOnly Cookie，组织/班级/活动归属在服务端实时复查。管理者角色不能访问别人创建的私有活动或跨组织文件；参与者只修改本人分配任务、提交材料与反馈。公开报名回执用取消凭证授权，不公开私有名单。安全过滤器、业务权限与审计分别承担入口、资源和追溯职责。

知识正文与向量原子更新，检索同时过滤组织与向量来源，保存来源 ID/版本等证据。模型/离线与检索状态来自服务端，不能信任模型自报依据。

RecapStore 锁内保存统计快照和版本，RecapService 在网络调用前筛选聚合白名单；AI 再校验且不注入 RAG，反馈原文不传模型。正文、统计和生成状态持久化，迟到结果不能覆盖已结束的生成记录。生成与活动结束是两个独立事务。

签到快照为追加式活动成员集合；当前资格决定能否操作，历史快照决定统计分母。就绪活动保存开放设置可追加成员，结束后不追加且停止新签到，反馈需已签到；报名、签到和反馈是不同业务数据，不互相冒充。

ExportService 显式选必要列，经权限检查后由 CsvExport 输出 BOM、引号转义与公式防护。模板只保存通用蓝图，来源提取脱敏，应用通过幂等记录创建草案，沿用既有人工确认链路。

## 6. 前端交互与错误处理

React Router 按登录与角色提供页面入口；接口仍独立检查资源权限。共享请求层处理错误与重新登录，表单在失败时保留输入。资源版本冲突提示用户刷新核对，已编辑内容不因轮询静默覆盖。任务、通知和运行状态用文字与颜色共同表达。

下列视觉规则延续现有页面与全局 CSS；新增功能应复用组件与设计令牌，部署/运维参数留在团队资料中。

## 界面与交互规范

本项目的界面语言参考 [Shipkit](https://shipkit.sh/) 的现代开发者产品风格，但不复制其品牌、文案、图标或页面结构。核心目标是让复杂的班级事务看起来直接、可信、可执行。

## 视觉原则

1. **内容先于装饰**：使用近黑、白和中性灰建立层级，颜色只表达焦点与状态。
2. **大标题，小噪声**：页面标题使用紧凑的大号粗体；解释文字短而清楚。
3. **边框代替重阴影**：卡片主要使用 1px 中性边框，阴影只用于浮层和重点区域。
4. **AI 区域像工作终端**：Agent 输入与活动编排使用深色点阵面板，与普通业务卡片区分。
5. **状态必须可辨认**：成功、等待、失败同时使用文字和颜色，不只依赖色彩。

## 页面模式

### 导航与工作台

- 桌面端使用 252px 浅色侧栏，当前入口为黑底白字。
- 主要内容宽度不超过 1240px，保持足够留白。
- 第一项关键指标使用黑色反转卡片，其他指标使用白色卡片。
- 手机端侧栏变为顶部图标导航，页面改为单列且不产生横向滚动。

### Agent 与活动编排

- 深色面板表示“输入自然语言并交给系统处理”的区域。
- 点阵只作为低对比度背景，避免干扰文字。
- 输入框与深色面板同色，边框形成结构；主执行按钮使用白底黑字。

### 表单与弹窗

- 控件高度不低于 38px，焦点使用清晰的黑色边框和外环。
- 弹窗使用 18px 圆角与背景模糊，危险操作使用红色语义样式。
- 登录页采用左右分区：价值说明与账号操作分离。

## 动效与无障碍

- 页面进入只使用轻微上移和透明度变化，不使用持续装饰动画。
- 支持 `prefers-reduced-motion`，用户要求减少动画时关闭过渡。
- 所有交互控件提供 `:focus-visible` 状态。
- 正文、边框与状态色需在浅色背景上保持可读对比度。

## 文件职责

- `web/src/styles/global.css`：全局令牌、重置、点阵画布、焦点和动效（整合自旧 `frontend/theme.css`）。
- 页面组件样式：随各页面组件维护在 `web/src/pages/*.tsx`（原 `frontend/workspace.css`、`styles.css`、`portal.css` 已并入）。
- 公共布局组件：`web/src/components/Layout.tsx`（侧边栏壳）。

新增页面应优先复用这些令牌与组件模式，不要重新引入紫色渐变、厚重阴影或独立字体体系。
